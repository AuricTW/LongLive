# RTX4090 BF16 inference

The opt-in SM8.9 backend reduces repeated launch/projection work while retaining
the original BF16 policy, fresh observation VAE, unmerged FP32 LoRA and inference
schedule. It needs neither Blackwell NVFP4 nor a FourOverSix native build.
Default reference and the other hardware profiles retain their existing paths.

Both `longwam build rtx4090` and `longwam build rtx4090 --check-only` report
that no native build is required and exit successfully, without reading native
sources, checking CUDA or creating a build directory. This is not a check
of GPU availability or inference compatibility.

## Select the backend

Use `hardware=rtx4090` with the validated synchronous H32/V4/A10 settings.
This CPU planning example loads no weights or simulator:

```bash
longwam eval libero --dry-run hardware=rtx4090 action_horizon=32 \
  execute_steps=10 replan_steps=10 num_inference_steps=10 seed=1
```

Remove `--dry-run` after providing the checkpoint, matching V4 configuration,
statistics and simulator setup. Video steps come from `model.imagine_infer_steps`;
the CLI does not accept an undeclared video-step policy_options key.
For an already loaded CUDA evaluation model:

```python
from longwam.runtime.backends import prepare_backend

model.eval().requires_grad_(False)
state = prepare_backend(model, "rtx4090")
print(state.to_dict())
```

Load the full checkpoint and any unmerged adapters before preparation. Keep the
existing preprocessing/policy adapter. Preparation is idempotent for this backend;
mixing prepared backends or rebinding parameters requires a fresh model. The path
is inference-only and single-request; concurrent calls on one prepared model
are unsupported. It does not accelerate training or change the control cadence.

## Tested contract and design

Linux RTX4090/SM8.9, PyTorch2.7.1+cu128, Triton 3.3.1, NumPy 2.2.6, Pillow 13.0.0,
sequential IDM, batch1, 13 observation frames, four clean/two future latent
frames, H32, four video/ten action steps, CFG1, original CPU-seeded noise.
Primary official LIBERO inputs are 224x448 with P48 and R10. Checkpoint-specific
action/proprio/statistics and original BF16/FP32 parameter dtypes are retained.
Quantization, merged LoRA, supplied clean latents, tiled/streaming VAE and async
execution are outside this validated path. Admission/call guards reject the
listed incompatible settings; untested checkpoints, dimensions and runtimes
are not certified by these finite checks.

CUDA Graphs use stable buffers and replay original work. Context projections
refresh once per request. Producer epochs and source identity protect graph
inputs; FP32 weight casts remain live for unmerged adapters. Shape-preserving
GEMMs and staged BF16 rounding avoid a packed-GEMM/changed-rounding shortcut.
Clean-prefix retention is confined to the current request. Observations, fresh
VAE encodings, generated noise and policy outputs are not reused across requests.

## Actual measurements and numerical scope

On one 24564 MiB RTX4090 at its unchanged pre-existing 480 W limit, with two fresh
processes per backend and 32 recorded official input/seed cases per process:

| Metric | Reference mean of process medians | RTX4090 mean of process medians | Speedup |
| --- | ---: | ---: | ---: |
| Full policy + CPU actions | 0.914134 s | 0.371463 s | 2.460902x |
| This harness request, including image/state preparation | 0.964081 s | 0.421364 s | 2.288001x |

Ratios use means of process medians. All 64 paired normalized actions/commands
and independent repetitions matched byte-for-byte. Current-main long-order
replay also matched 613/613 pairs; existing private trained unmerged adapters
matched 30/30. Model parameters remained unchanged. These are observed finite
comparisons, not a guarantee for every input or model. The same-input historical
investigation reproduced 4904/4904 original outputs across eight fresh processes;
reference-only image swaps reproduced the original q14 action difference.
Recorded image variation explains that tested discrepancy, while original
renderer versus hidden-simulator-state provenance remains unresolved.

Model time includes fresh observation encoding, all video/action denoising and
CPU action return; request time also includes this saved-history harness's
13-frame preparation. Neither includes imagined-RGB decode, initial T5 encoding,
loading, hashing or graph warmup. Startup/capture and memory are recorded
separately. Ordinary incremental history buffering has different frontend costs.
Do not infer an episode-time, energy, stock450W or official5090/DGX speedup.

The older native cohort succeeded 40/40 versus 40/40 at one initial state/seed per
task. It is not a new current-main cohort, the official 50-state score or a
noninferiority study. This round's replay adds no new native success-rate claim.
These Strict measurements exclude the numerically different Fast mode described below.

The [independent validation attachment](https://github.com/AuricTW/LongLive/releases/tag/rtx4090-validation-20261021) includes the public harness,
recorded official cases, q14 probe, source/weight hashes, actual measurements,
startup costs and detailed limits. Large research artifacts are kept outside
the runtime patch.

## Regression tests

```bash
PYTHONPATH=src python -m unittest discover -s tests/runtime -p 'test_sm89*.py' -v
# On an idle SM8.9 device, explicitly include the three actual GPU tests:
RUN_SM89_GPU_TESTS=1 PYTHONPATH=src python -m unittest discover \
  -s tests/runtime -p 'test_sm89*.py' -v
```

The attachment distinguishes measured file hashes from LF-formatted Git files;
compiled Python code and tokenizer-visible text are identical. Its restorer
recreates exact measured bytes before running the unchanged GPU-tested harness.

The original nine Strict tests cover admission, request refresh, source/epoch invalidation,
live FP32 adapter casts, shape-preserving GEMMs and staged BF16 rounding.
Fast adds four CPU admission and installation tests to the same discovery command.
Three Strict tests require CUDA; skipped tests are not passes. Full checkpoint/LoRA and
simulator evidence are separate from these small public regressions.

## Explicit experimental Fast mode

Strict remains the default. For the separately selected, numerically different
Fast mode and its measured limitations, see [RTX4090 Fast](RTX4090_FAST.md).
